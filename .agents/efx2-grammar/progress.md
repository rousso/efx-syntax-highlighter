## How the sync works (P0.2)

- **Sources.** The forks are read from GitHub at full commit hashes: the API resolves a short hash and lists the commit's files once (`git/trees`, recursive), so files in a subfolder of the corpus folders are not missed; the files come from raw.githubusercontent.com. `GITHUB_TOKEN` is sent to the API only, when it is set; the workflow sets it.
- **Generated grammar.** antlr-ng's JavaScript target writes code for the `antlr4` runtime, not for `antlr4ng`. The sync generates TypeScript, which targets `antlr4ng`, and removes the types with Node's `module.stripTypeScriptTypes` (Node 22.13 or later). The stripped lexer is byte-identical on Node 22.14.0 (the workflow's) and 22.23.4. antlr-ng 1.0.10 cannot be imported as a library (its entry exports a type as a value), so the sync runs its command line. The parser is generated in a temporary folder under `node_modules/.cache/` and not kept.
- **Words.** The candidates are the quoted words of `EfxLexer.g4`; each is lexed by the generated lexer in each mode, as the toolkit's `CatalogueCompletenessTest` finds a word's token by lexing it. Function names: the spellings of the tokens that can start `builtInFunction` (read from the parser's ATN). Keywords: the words reserved in `DEFAULT_MODE`, `SKIP_WHITESPACE`, `TEMPLATE` or `EXPRESSION`, that is, lexed as a token other than `Identifier` or `FreeText`; since P1.2, except the words the parser reads only as a function name (below). Asset and label types: the words lexed as `AssetType` and `LabelType` in `LABEL`. Format options: the words lexed in `FORMAT`.
- **Proxy.** Node's `fetch` does not read `HTTPS_PROXY`; behind a proxy, run the sync with `NODE_USE_ENV_PROXY=1` (Node 22.21 or later), as was done here.

## How the conformance test works (P1.1)

- **Match.** A token of the lexer is matched when the editor has a token of the name `TokenNames` gives, starting at the same position, and the next token starts at the same position on both sides. A file matches when every token of the lexer is matched and the editor has no other token.
- **Lexer side.** Every token on the default channel. Tokens on another channel are left out: in the corpus, `WS`, `Whitespace` (from `SkippedWhitespace`), `SkippedComment`, `EmptyOrCommentLine`, `EndOfLineComment` and `ExpressionComment`, 167,188 tokens. This is the only rule that leaves tokens of the lexer out.
- **Editor side.** The leaves of the tree without comments; the text between two leaves, when not blank, as a token with no name; each parse error as a token named ⚠ where it starts. Comments are left out on both sides, since the lexer keeps some inside another token (the comment after a template line's `;` is part of its `Semicolon`).
- **Positions.** In UTF-16 units on both sides: the lexer counts characters, so its positions are converted. The corpus is ASCII at the pin.
- **Table.** `test/conformance/TokenNames.js` has a row for each of the 105 kinds of token the lexer makes in the corpus: 6 with the same name, 85 with the editor's node of the same meaning, 14 with no node yet. A kind missing from the table fails the test.
- **Pins.** Files and tokens matched, at the top of `test/conformance.js`. A change in either direction fails the test, and the message gives the line to paste.

## How the words reach the grammar (P1.2)

- **Specializer.** The grammar reads every word as `Identifier` and declares `wordToken` (`src/efxWords.js`) as Lezer's external specializer for it: `@external specialize`, not the plan's first wording `@external extend`, because `wordToken` gives a kind only where the parser can take it (`stack.canShift`), so no word is read two ways.
- **Order.** Label words (asset types, label types), then keywords, then function names; the first kind that has the word and that the parser can take. Label words before keywords as the old token precedence had them (in `#{auxiliary|text|buyer}`, `text` is a label type); keywords before function names so that `is not present` reads `not` as a keyword.
- **Keywords.** Every word the lexer reserves at the start of a line, in template text or in expressions, except the words the parser reads only as the name of a built-in function. The sync asks the generated parser which tokens it reads other than as the first token of `builtInFunction` (`AntlrGrammar.tokensReadOnlyAtStartOf`, since the phase 1 simplify pass): of the function tokens, `Not`, `Empty`, `Text`, `Number`, `Indicator`, `Date` and `Time`. So `not`, `empty`, `text`, `string` (which the lexer reads as `Text`), `number`, `indicator`, `date` and `time` are in both `keywords` and `functionNames`.
- **Package contents.** The build copies `efxWords.js` and `generated/words.js` into `dist/`, where the parser loads them; the published package gains these two files. They are package contents, not exports: `efx()`, the exports and the version are unchanged, so decision 4 is untouched.
- **What stays until phase 2.** The words inside today's compound tokens: the line words (`LET`, `WITH`, `WHEN`, `OTHERWISE`, `DISPLAY`, `INVOKE`, `INDEX`, `BY`), the boolean words in the literal token, the type words in `text:` and `value` in `$value` and `#value`. Gate 1 reads "no word list lives in the grammar file" (plan, as updated).

## How expressions are read (P2.1)

- **Rules.** Every rule of `Efx.g4` an expression uses, ported in its order: the expression and selector blocks, `expression` with its 29 alternatives (one left-recursive rule with `@precedence` markers in the order of `Efx.g4`), function invocations, parameters and arguments, type declarations, iterators, literals, references, contexts, predicates, `fieldProperty` and `codelistReference`, and `builtInFunction` with its seven sub-rules (72 alternatives, written with one parametrised rule `call<name, args>`). Left out: `parameterValue` and its eight sub-rules (an entry point of the toolkit that no file reaches) and `dynamicFunctionInvocation` (rules files, P2.3). Tokens take the lexer's names and spellings.
- **Node names.** As ANTLR's parse tree: a rule is a node named as the rule with a capital first letter; a rule whose alternatives are labelled gives way to its alternatives (`expression` is the group `Expression`). Where a node would only repeat a token's name, the token stands for it: a built-in function's alternative (its token names the call) and a rule named like a token (`stringLiteral`, `dateLiteral`, `timeLiteral`, `ShorthandFieldValueReferenceFromContextField`).
- **The colon after a field.** `BT-1-Lot:isMasked` (a property of the field) and `BT-1-Lot:rawValue` (of its value) start with the same two tokens; GLR markers (`~linkColon`, `~fieldColon`) let the parser keep both readings until the word after the colon.
- **Words.** The sync writes `expressionTokens`, the token the lexer makes of each word it reserves in EXPRESSION mode (160 words), and no longer `functionNames`. `src/efxWords.js` is a contextual external tokenizer: it reads a word as the lexer reads an `Identifier`, and returns the table's token where the parser can take it; otherwise, for the template rules until P2.2, a label word or keyword as before; otherwise nothing, and the word is an `Identifier`. It replaces P1.2's specializer, whose answer for a position Lezer shares between the two readings at the field colon (`BT-1-Lot:isMasked` failed with it).
- **Template rules until P2.2.** They read their expressions through the ported rules. Changes forced by the port: the outline number is the token `OutlineNumber`; the template's `${...}` is `FormattedExpressionBlock` (its name in `Efx.g4`; the theme's selector follows); the compound token `Type` is gone (declarations and parameters read a type or `context`, then the colon); a parameter's `Identifier` alternative is gone (a field context reads it); `INVOKE` reads an expression (the old `item` rule went with the old expression rules); an asset id in a label block may be a `BtId`, now a token of its own as in the lexer.
- **Tests.** `test/trees.js` (run by `npm test` after the sample test) reads each entry of `test/trees/entries.js` with both parsers: the editor's with the `SingleExpression` top, ANTLR's from `test/oracle/EfxParser.js`, which the sync now writes with `Efx.g4`. `OracleTree` names ANTLR's nodes by the rule above. ## How template files are read (P2.2)

- **Rules.** The rules of `Efx.g4` a template file uses, in its order: the file and its sections, global declarations (variables, dictionaries, functions), template lines and declarations with their indentation, the template text with its blocks (text, label, expression and link blocks, format options), `WHEN`, `OTHERWISE`, `DISPLAY` and `INVOKE`; and the declarations a template file shares with rules files (variable and context declarations, variable lists and initialisers, the include directive). `TemplateFile` is the default top; `SingleExpression` stays for the tree test.
- **Lexer modes as parse state.** `src/lexer/LexerModes.js` is one contextual external tokenizer. It finds the mode of `EfxLexer.g4` from the tokens the parser can take (`stack.canShift`), trying the modes in this order: TEMPLATE where a template can go on, the start of a template, LABEL, the name after a prefix, FORMAT, the line start (DEFAULT and SKIP_WHITESPACE) and EXPRESSION, which is the rest. Each mode is a class (`LexerMode` and its subclasses): it hides what the lexer hides there, then reads the tokens whose reading depends on the mode; where it reads none, the grammar's own tokens are read. `LexerInput` reads the characters, `ReservedWords` the words of a mode's table.
- **Skip.** One skip set, `space` and `Comment`, which the tokenizer makes only where the mode hides them: whitespace stays significant in template text, and line ends and comments are hidden in expressions. Label blocks skip nothing (`@skip {}`). A context tracker (`TemplateEnd.js`) marks the place right after a `DISPLAY` template, where the lexer is still in TEMPLATE mode.
- **Words.** The sync writes four tables, the token the lexer makes of each word it reserves at a line start (`lineTokens`, also read with a trailing blank, as `DISPLAY`), in template text (`templateTokens`), in format options (`formatTokens`) and in an expression (`expressionTokens`); `OTHERWISE` takes a following `DISPLAY` in every mode, as the lexer does. A reserved word is its token wherever the parser can take that token or a name, as the lexer reads it, which closes the divergence of reserved words as field names.

## How rules files are read (P2.3)

- **Rules.** The rules of `Efx.g4` a rules file uses, in its order: the file, includes, API endpoints, dynamic functions with their error clause, global and stage variables, validation stages with their header, rule sets, simple, conditional and fallback rules with their clauses (`WHEN`, `ASSERT`, `REPORT`, `AS`, `FOR`, `IN`, `SCOPE`), severities, rule ids, notice type lists and ranges. `RulesFile` is the second top.
- **Rules and conditional rules.** `Efx.g4` reads a rule set as `rules` (simple and conditional rules, at least one) or as `conditionalRules` and a fallback rule. Both start with conditional rules, and Lezer's GLR parser drops one of two parallel readings once both have more than 500 tree entries, so a long run of conditional rules failed with two separate rules. The grammar reads the run once (`conditionalRuleRun`, which has no node) and lets the token after it decide; it accepts the same rule sets, and the trees are those of `Efx.g4`.
- **The line start.** After a rule the parser can take the same tokens whether the rule ended with `;` or not, but the lexer is at the start of a line only after the `;`; before it, it is still in EXPRESSION mode. A context tracker (`src/lexer/LexerContext.js`) records that the parser has just read a `;`, a line end, an include, a stage header or a section header, and the line mode is active there; it is the file's start value too, so blanks before a single expression now fail, as in ANTLR. It also takes over the mark of a closed template from `TemplateEnd.js`. The skip tokens leave it as it is.
- **Includes.** The lexer reads `#include` only in DEFAULT mode, so `IncludeDirective` leaves the grammar's tokens and the line mode reads it. After a rule set without `;` the `#` is a `HashPrefix` in both parsers (two places in `rules.efx`, parked).
- **Stage headers.** `StageHeaderStart` is a token of the grammar, read before `Minus`; the header's name and end are read by a mode of their own (`StageHeaderMode`) that hides nothing, so the blanks before the closing dashes stay with `StageHeaderEnd`, as in the lexer.
- **Phrases.** The lexer reads some words with the next word as one token: `OTHERWISE DISPLAY` and, in an expression, `OTHERWISE ASSERT` and `OTHERWISE REPORT`. The sync now finds them by lexing two words with whitespace between (a blank, a tab, a line end and a mix) and lists each in the tables as the two words; `ReservedWords` reads the second word as the lexer does, whole word or not. P2.2's hand-written rule for `OTHERWISE DISPLAY` is gone.
- **The attribute's slash.** A `/` followed by `@`, with only whitespace and comments between, is a token of its own (`AttributeSlash`, named `Slash` in the tree), so the parser no longer decides at the `/` and `2 * 3 / 4` groups as in ANTLR. The tree of `rules.efx` is well formed with it (findings).
- **Tests.** The conformance test reads each corpus folder with its top. The tree test gains `rules` entries, whole rules files read with the `RulesFile` top: 17 valid files, 5 mistakes and 2 divergences. The token table names the 12 kinds of rules files as the lexer does.
- **Speed.** `rules.efx`, 575 KB and 17,177 lines, parses in 830 to 980 ms over six runs (ANTLR about 515 ms). To watch at P4; an editor parses incrementally and only the visible part first.

## How the colours are given (P2.4)

- **The style table.** `EFX_STYLES` in `src/efxTheme.js` (in `src/efxHighlighting.js` since P2.5) gives each kind of node its highlight tag, grouped by tag with a comment per group, and `efxHighlighting` is `styleTags(EFX_STYLES)`. Each kind takes the tag its kind had in 0.2.1; a kind 0.2.1 never coloured takes the tag of the nearest kind it had (the design doc's table). `efxColors`, the tag-to-colour map, does not change. A kind not listed stays plain, as in 0.2.1: `;`, `,`, outline numbers, indentation, line ends, the blanks of template text and parse errors.
- **Names, not words.** The table names nodes, and a node by its parent where one token plays two parts (`BuiltInFunction/Text` is a call of `text(...)` or `string(...)`, `Text` alone the type of `text:`). A function's token is the first child of `BuiltInFunction`, and a style rule cannot select a first child, so 65 function tokens are listed by name and the 7 words that are also a type or an expression word (`text`, `not`, ...) by their parent, 72 in all, every function token of the grammar. A token the grammar adds later stays plain until it is listed.
- **One tag per token.** `${`, `#{`, `@{` and `&{` are one token each, as in the lexer, and take the braces' tag (bracket); the `$` and `#` lose the bold 0.2.1 gave them. A few tokens hold blanks or line ends, as the lexer's do (` OTHERWISE DISPLAY` with the blanks before it, a stage header's end); on blanks no colour shows.
- **The test.** `StyleDump` reads a text with its top through `highlightTree` and writes each piece of text the highlighter styles as its line and column, its tags as Lezer writes them (`function(keyword)`) and its text. `test/styles.js` compares the dumps of the sample and of `stage-4m.efx` with `test/styles/sample.txt` and `test/styles/stage-4m.txt` and prints the first ten differences; `node test/styles.js --write` writes them anew, so the commit that changes a colour shows each change. It also checks that every name in the table, split at blanks and `/`, is a node of the grammar: a name that is not one styles nothing and says nothing, which is how strings went uncoloured in 0.2.1 (its rule named `String`).
- **Over the corpus.** Every kind of token that occurs in the 56 corpus files, the sample and the tree entries has a tag or is one of the plain ones (checked once, outside the repository). Rules files are coloured for the first time.

## How an application uses the package (P2.5)

- **One function.** `efx(kind)` gives an editor one kind of EFX text, `"template"`, `"rules"` or `"expression"`: a CodeMirror language whose parser reads from that kind's top (`TemplateFile`, `RulesFile`, `SingleExpression`), and the EFX colours as a fallback highlighter, which CodeMirror uses only where no other colours are set. The three languages are made once and share the parser. A kind that is not one of the three is refused with an error naming them.
- **Tags and colours.** The tags are part of the grammar: `grammar/efx.grammar` reads them from `src/efxHighlighting.js` (`@external propSource`), so every parser of the package carries them, the one in an editor and the one the tests read. The colours are the application's choice: `efxHighlightStyle` in `src/efxTheme.js`, beside `efxTheme`, the editor's look. Before P2.5 the tags lived in the theme file, so the parser loaded CodeMirror's view through it.
- **The test.** `test/package.js` loads `dist/index.js`, as an application does, and makes editor states with no view (`EditorState`, `ensureSyntaxTree`, `highlightingFor`), so it runs in Node.

## How the editor completes (P3.2)

- **What the parser can take.** `src/completion/ExpectedTokens.js` parses the text before the word at the cursor again, reusing the editor's tree, with the lexer modes' tokenizer wrapped. Where a parse stack stands at the word's start, the wrapper asks it which tokens it can take (`Stack.canShift`) and finds the lexer's mode there (`lexerModeAt`), whose words (`words()`, from the tables of `src/generated/words.js`) are offered when the stack can take their tokens. The parse is strict: it stops at the first error, so no answer comes from Lezer's repair of an error. Recording every tokenizer call at the end of a lenient parse was tried first: the repair stacks offered functions after `#{`.
- **What is offered.** `src/completion/EfxCompletions.js`: the words, described by the toolkit's list (`CompletionItems.js`: a function as a call where the parser can also take `(`, a bare word elsewhere; its kind and data type); field and node ids from `efxSymbols` where the parser takes one; the variables of the text (`Variables.js`) where it takes a `$`. Every spelling the lexer reads, a phrase only in one case. Template text opens the list only when asked for; nothing inside a comment or a string.
- **The test.** `test/completions.js` asks the language's completion source as an editor does (`languageDataAt('autocomplete')`, `CompletionContext`) on editor states with no view, and applies a picked call to a stand-in for the view.
